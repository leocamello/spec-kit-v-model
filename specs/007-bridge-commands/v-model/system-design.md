# System Design: Bridge Commands

**Feature Branch**: `feature/007-bridge-commands`
**Created**: 2026-04-26
**Status**: Draft
**Source**: `specs/007-bridge-commands/v-model/requirements.md`

## Overview

The bridge-commands feature is decomposed into three top-level command subsystems
(`v-model.plan`, `v-model.tasks`, `v-model.implement`) plus a set of cross-cutting
modules and services that the three commands share. The cross-cutting components
implement the additive-enrichment pattern, the spec-kit-core compatibility layer,
the pre-implementation gate (which delegates to existing deterministic scripts),
and the safety-net checks (hallucination guard, source-region preservation). This
decomposition isolates the "what each command does" responsibility from the
"how the contract with spec-kit core is preserved" responsibility, so the
compatibility layer can be tested and evolved independently of the command
business logic.

No domain overlay is loaded for this feature (`v-model-config.yml` is absent at
the repository root); only the base IEEE 1016 design views are populated, and no
safety-integrity sections (FFI, restricted complexity, ASIL allocation) are
required.

## ID Schema

- **System Component**: `SYS-NNN` — sequential identifier, never renumbered.
- **Parent Requirements**: Comma-separated `REQ-NNN` list per component
  (many-to-many). Coverage is computed against the active requirement set in
  `requirements.md`.
- Example: `SYS-001` with Parent Requirements `REQ-001, REQ-002, REQ-003, ...`
  — the component satisfies every listed requirement.

## SYS-006 Algorithm Specification (Hallucination Guard)

> **Rationale:** ISO 14971 §5.3 (HARA design input) and IEC 60812 §6 require
> that risk controls reference an explicit design specification. This section
> exists so that hazard-analysis (HAZ-007 / HAZ-012 / HAZ-013) can compute a
> defensible likelihood for SYS-006 false-negative and false-positive
> outcomes. Surfaced by peer-review finding PRF-HAZ-007 and partially by
> PRF-SYS-001 (operational-state observation).

**Type:** Deterministic, regex/AST-based ID validator. **No LLM invocation
inside SYS-006 itself.** This is a non-negotiable design constraint:
because the upstream content under inspection (`// Implements <ID>`
comments) was generated by an LLM (HAZ-007 likelihood = "Occasional"),
SYS-006 MUST be deterministic to provide independent verification.
Introducing LLM evaluation inside SYS-006 would replace one
non-deterministic step with another and invalidate the false-negative
likelihood claim ("Remote") in HAZ-012.

**Algorithm:**

```pseudocode
FUNCTION verify_ids(generated_files: list[(Path, str)],
                    vmodel_id_set: set[str]) -> VerifyResult:

    hallucinations = []                      // accumulator: (file, line, id)
    pattern        = COMPILE("(?i)\\bImplements\\s+([A-Z]+(?:-[A-Z]+)?-[0-9]+(?:[A-Z][0-9]?)?)\\b")
    //                                                ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    //                                                matches REQ-001, REQ-NF-002, ATP-024-A, UTS-013-A2, HAZ-009, etc.

    FOR each (path, content) IN generated_files:
        comment_lines = MOD-019.extract_comment_lines(path, content)   // language-aware (#, //, --, etc.)
        FOR each (line_no, line_text) IN comment_lines:
            FOR each match IN pattern.finditer(line_text):
                claimed_id = match.group(1)
                IF claimed_id NOT IN vmodel_id_set:
                    hallucinations.append((path, line_no, claimed_id))

    RETURN { valid: len(hallucinations) == 0, hallucinations: hallucinations }
```

**Properties:**

| Property | Value | Justification |
|----------|-------|---------------|
| Determinism | Total | Pure function of `(generated_files, vmodel_id_set)`; no I/O, no LLM, no clock, no randomness. Same inputs ⟹ same outputs across hosts and runs. |
| False-negative rate | 0 by construction | Every `Implements <ID>` comment recognised by the regex is checked against `vmodel_id_set`. The only residual false-negative path is a comment whose surface form does not match the regex (e.g. obfuscated whitespace) — addressed by REQ-NF-002 conformance tests at unit level. |
| False-positive rate | 0 against authoritative ID set | An ID is reported as a hallucination only if it is absent from `vmodel_id_set`. The set is built from the V-Model artifact files themselves (ARCH-019), so by definition it is the ground truth. |
| Time complexity | O(N · L) | N = total bytes of generated source; L = average comment-density. Linear in input size; runs comfortably within the per-run budget. |
| LLM-eval supplement | None at gate time | A separate LLM-based eval (`structural-eval`, REQ-NF-002) is run in CI as a *secondary* defense, but its result is NOT consulted by SYS-006 at commit time. SYS-006 alone is the merge-blocking control. |

**Authoritative ID set construction (`vmodel_id_set`):**

`vmodel_id_set` is the union of every ID extracted by ARCH-019 from the
V-Model artifact set: `REQ-NNN` (incl. `REQ-NF-NNN`, `REQ-IF-NNN`,
`REQ-CN-NNN`), `ATP-NNN`, `SCN-NNN`, `SYS-NNN`, `STP-NNN`, `STS-NNN`,
`ARCH-NNN`, `ITP-NNN`, `ITS-NNN`, `MOD-NNN`, `UTP-NNN`, `UTS-NNN`,
`HAZ-NNN`, plus `[DEPRECATED]`-tagged IDs (kept in the set so that
generated comments referencing a deprecated-but-still-traced item are
NOT flagged as hallucinations).

**Failure modes covered by HAZ-012 / HAZ-013:**

| HAZ | Direction | Residual risk justification |
|-----|-----------|-----------------------------|
| HAZ-012 (false-negative) | Guard misses an invalid ID | Residual = Tolerable. The deterministic regex+set-lookup cannot miss an ID that the regex recognises; the only residual likelihood is a regex-evasion bug (mitigated by UTP-013 boundary tests including UTS-013-A2 with the REQ-999 phantom fixture) plus the SYS-013 CI harness as a second line of defense. |
| HAZ-013 (false-positive) | Guard rejects a valid ID | Residual = Acceptable. The set-membership test cannot reject an ID that is in `vmodel_id_set`; the only residual likelihood is an ARCH-019 parser bug (mitigated by UTP-024 round-trip tests against every artifact in the V-Model). |

**What SYS-006 does NOT do** (out-of-scope, by design):

- Does not validate semantic correctness of the comment ("does the
  generated function actually implement REQ-008?"). That is the role of
  the LLM eval (REQ-NF-002, secondary defense) and human peer-review.
- Does not parse Markdown content or rebuild the canonical ID set
  itself — that is delegated to ARCH-019.
- Does not call out to any external service or LLM. SYS-006 is a pure
  in-process function with no network surface.

## Glossary

| Term | Definition |
|------|-----------|
| Additive enrichment | The pattern (owned by SYS-005) of layering V-Model traceability metadata onto canonical spec-kit-core artifacts as HTML comments and optional Markdown sections that core tooling harmlessly ignores. |
| Bridge command | A V-Model command (SYS-001, SYS-002, or SYS-003) that produces output in spec-kit-core canonical format, enabling downstream consumption by unmodified `speckit.*` commands. |
| Direct Path | The user path in which V-Model artifacts feed directly into SYS-003 without producing intermediate `plan.md` / `tasks.md`. |
| Fail-closed | A failure-handling policy in which an indeterminate or failed precondition causes the operation to abort rather than proceed; SYS-004 and SYS-006 implement this policy. |
| Full Ceremony | The user path in which every V-Model command (including SYS-001 and SYS-002) is run before SYS-003. |
| Hybrid path | Any user path that mixes `speckit.*` and `v-model.*` commands at any layer of the workflow; enabled by SYS-010's reduced-enrichment fallback and SYS-007's region preservation. |
| Pre-implementation gate | The composite check executed by SYS-004 on behalf of SYS-003 before code generation, comprising `build-matrix` plus the five `validate-*-coverage` scripts. |
| Round-trip property | The property (owned by SYS-010) that a `plan.md` produced by SYS-001 is valid input to `speckit.tasks`, and a `tasks.md` produced by SYS-002 is valid input to `speckit.implement`. |
| Target Source File | The field within each `MOD-NNN` entry in `module-design.md` declaring the source-file path(s) the module implements; SYS-003 writes generated code to these paths. |
| V-Model-managed region | A span of generated content in a source file demarcated by language-appropriate marker comments and owned by SYS-007; content outside such regions is preserved across re-runs. |
